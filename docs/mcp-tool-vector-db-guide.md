# MCP、Tool 与向量数据库学习文档

## 1. 这份文档讲什么

这份文档主要讲三件事：

- `MCP` 是什么
- `Tool` 是什么，怎么使用
- 普通数据怎么转换成“可用于向量数据库检索”的数据

如果你现在正在做 AI 应用、知识库问答、RAG 或智能助手，这三块内容基本是连在一起的。

---

## 2. 什么是 Tool

### 2.1 最简单的理解

`Tool` 可以理解成“给 AI 额外接上的能力”。

模型本身只会：

- 理解文字
- 生成文字
- 做推理

但是模型默认不会：

- 访问数据库
- 调接口
- 查本地文件
- 发 HTTP 请求
- 执行命令
- 搜索知识库

所以我们要给模型接 `Tool`。

### 2.2 Tool 的作用

常见工具能力包括：

- 查询数据库
- 调用天气接口
- 调用支付接口
- 调用公司内部系统
- 读取本地文件
- 执行脚本
- 向量检索

也就是说：

> Tool 不是模型本身，而是模型“可以调用的外部能力”。

### 2.3 Tool 的典型调用过程

一般流程是：

1. 用户提问
2. 模型判断是否需要调用工具
3. 模型输出工具名和参数
4. 系统执行工具
5. 工具返回结果
6. 模型再根据工具结果生成最终回答

例如：

```text
用户：今天北京天气怎么样？
模型：需要调用 weatherTool(city=北京)
系统：执行 weatherTool
工具返回：晴，25℃
模型：今天北京晴，25℃
```

### 2.4 Tool 的本质

从技术上看，Tool 往往包含这几部分：

- `name`：工具名
- `description`：工具说明
- `input schema`：入参结构
- `handler`：真正执行的后端代码

你可以把它理解成“给模型暴露出去的一个函数”。

---

## 3. 什么是 MCP

### 3.1 最简单的理解

`MCP` 是 `Model Context Protocol`，可以理解成：

> 让模型、安全地接入外部工具、资源、上下文的一套协议。

它的重点不是“某一个工具”，而是“怎么把工具和资源规范化地提供给模型使用”。

### 3.2 MCP 解决什么问题

如果没有 MCP，不同系统接工具通常很乱：

- 每个工具接法都不一样
- 参数格式不统一
- 返回格式不统一
- 权限控制不好做
- 客户端和服务端很难复用

MCP 的价值就在于把这件事标准化。

### 3.3 MCP 的核心思想

MCP 一般会把模型可用的外部能力分成几类：

- `Tools`：可执行的能力
- `Resources`：可读取的资源
- `Prompts`：可复用的提示模板

所以 MCP 不只是工具调用，它更像是“模型与外部系统通信的标准层”。

### 3.4 你可以怎么理解 MCP

一个很好理解的类比是：

- `Tool` 像一个具体的插头
- `MCP` 像整套插座标准

也就是说：

- `Tool` 是具体能力
- `MCP` 是接入这些能力的协议和规范

---

## 4. MCP 和 Tool 的关系

很多人会把这两个概念混在一起，其实它们不是一层东西。

### 4.1 区别

`Tool` 是能力本身，例如：

- `searchDocs`
- `queryOrder`
- `getWeather`

`MCP` 是协议层，例如：

- 客户端如何发现有哪些工具
- 工具参数怎么定义
- 返回值怎么传回模型
- 资源怎么暴露

### 4.2 一句话区分

```text
Tool = 做事的功能
MCP = 让这些功能规范接入模型的方式
```

---

## 5. MCP 常见组成

### 5.1 MCP Server

`MCP Server` 用来暴露工具、资源、提示等能力。

例如一个公司内部的 MCP Server 可能提供：

- 查询订单工具
- 查询库存工具
- 读取产品文档资源

### 5.2 MCP Client

`MCP Client` 是接收这些能力的一方，通常是：

- AI 应用
- 聊天客户端
- Agent 框架
- IDE 中的 AI 助手

### 5.3 Resource

`Resource` 一般是只读上下文，例如：

- 一个配置文件
- 一份 API 文档
- 一张数据库表结构说明

它更像“给模型看的资料”。

### 5.4 Tool

`Tool` 是可以执行动作的，例如：

- 查数据库
- 下订单
- 调用搜索接口

它更像“给模型用的手”。

---

## 6. Tool 适合什么时候用

下面这些场景特别适合 Tool：

- 模型需要查实时数据
- 模型需要访问企业内部系统
- 模型需要执行某个明确动作
- 模型需要做精确计算
- 模型需要检索知识库

例如：

- 查用户余额
- 查订单状态
- 创建 API Key
- 搜索站点配置
- 检索向量数据库

---

## 7. MCP 适合什么时候用

下面这些场景特别适合 MCP：

- 你有多个工具要统一给模型使用
- 你希望工具和资源都规范化接入
- 你想做标准化的 Agent 能力接入
- 你想让不同客户端复用同一批能力

如果只是本地小项目，有时直接写 Tool 就够了。

如果是：

- 团队协作
- 多系统接入
- 多工具统一管理
- IDE / AI 助手 / 后台服务共用

那 MCP 会更合适。

---

## 8. 一个完整例子

比如你做一个“企业知识问答助手”。

它可能有下面这些能力：

- 读取产品文档
- 查用户权限
- 调用向量检索
- 调用大模型生成答案

那么可以这样理解：

- `vectorSearchTool`：具体工具
- `getUserRoleTool`：具体工具
- `MCP Server`：统一把这些工具和资源提供给 AI

用户提问时，模型可能这样工作：

1. 先读取知识说明资源
2. 再调用向量检索工具
3. 如果结果不足，再调用别的系统工具
4. 最后组织答案

---

## 9. Tool 和向量数据库有什么关系

在 RAG 系统里，向量检索通常就是一个 Tool。

例如：

```text
tool name: searchKnowledgeBase
input:
  - query
  - topK
output:
  - matched documents
  - scores
```

也就是说：

- 向量数据库本身是存储层
- 向量检索接口是能力层
- 对模型来说，这个能力通常表现为一个 Tool

所以在 AI 系统里，你常会看到：

```text
用户问题 -> 模型决定调用 searchKnowledgeBase -> 工具查向量库 -> 返回结果 -> 模型回答
```

---

## 10. 什么叫“转换成向量数据库”

严格来说，不是把“数据库整体变成向量数据库”。

更准确的说法是：

> 把原始文本数据转换成向量，并存入支持相似度检索的存储系统中。

所以真正发生的事情是：

- 原始内容先被提取出来
- 文本被切片
- 每个切片被转成向量
- 向量和原文一起存入向量库

---

## 11. 哪些数据可以转成向量库数据

常见可转换的数据包括：

- Word 文档
- PDF 文档
- Markdown 文档
- Excel 里的说明文字
- FAQ 问答
- 接口文档
- 产品手册
- 工单描述
- 聊天记录
- MySQL 表里的文本字段

注意：

不是所有字段都适合向量化。

更适合向量化的是“有语义的文本内容”，例如：

- 标题
- 描述
- 正文
- 备注
- 说明文档

像下面这些更适合做结构化过滤，而不是向量化：

- ID
- 状态码
- 创建时间
- 金额

---

## 12. 转成向量数据库的标准流程

### 12.1 第一步：收集原始数据

先明确知识来源，例如：

- MySQL 数据表
- 本地文件
- 网页内容
- 接口返回内容

### 12.2 第二步：文本清洗

清洗掉没有意义的内容，例如：

- HTML 标签
- 重复空格
- 无用符号
- 重复段落

### 12.3 第三步：文档切片

不要整篇直接向量化，要切片。

常见做法：

- 按标题切
- 按段落切
- 按固定长度切

例如：

- 每段 `300` 到 `800` 字
- 或每段 `500` 到 `1000` tokens`

切片的目的是让检索更精准。

### 12.4 第四步：生成 Embedding

调用嵌入模型，把文本切片转成向量。

例如：

```text
"API Key 创建方法"
-> [0.12, -0.33, 0.91, ...]
```

### 12.5 第五步：写入向量数据库

通常需要存三类数据：

- 原始切片文本
- embedding 向量
- 元数据

元数据例如：

- 文档标题
- 来源
- 标签
- 创建时间
- 业务类型

### 12.6 第六步：查询时做相似度搜索

用户提问后：

1. 把问题也转成向量
2. 去向量库做相似度搜索
3. 取 `TopK` 结果
4. 判断相似度是否足够高

### 12.7 第七步：把检索结果给大模型

这就是典型的 `RAG`：

```text
问题 -> 向量检索 -> 返回上下文 -> 大模型基于上下文回答
```

## 13. 一个最简单的结构示意

```text
原始数据
  -> 文本提取
  -> 文本清洗
  -> 文档切片
  -> embedding
  -> 向量库

用户问题
  -> embedding
  -> 向量检索
  -> 返回 TopK
  -> 交给大模型回答
```

---

## 14. 向量数据库里一般存什么

一条向量记录通常包括：

- `id`
- `chunk_text`
- `embedding`
- `source`
- `document_id`
- `chunk_index`
- `tags`
- `created_at`

也就是说，向量库不只是存向量，还要保留“这段向量原来对应的文本是什么”。

否则检索出来你也不知道该拿什么给模型。

---

## 15. 为什么不能直接把 MySQL 说成“向量库”

很多初学者会误解成：

```text
我把 MySQL 的数据导进去，就等于有向量数据库了
```

其实不是。

你需要多做一步：

1. 从 MySQL 中取出文本内容
2. 生成 embedding
3. 存到支持向量检索的存储里

如果你只是把文本存在普通 MySQL 表里，没有向量字段和相似度检索能力，那它还是普通数据库。

---

## 16. 向量数据库有哪些选择

常见方案有：

- `pgvector`
- `Milvus`
- `Qdrant`
- `Weaviate`
- `Elasticsearch` 向量检索

如果你是 Java 项目，入门很推荐：

- `PostgreSQL + pgvector`

因为：

- 学习成本低
- 数据也容易管理
- 适合做第一版 RAG

---

## 17. 如果你的原始数据在业务数据库里，怎么转

这里说的是最常见的场景：

你的业务数据本来在 MySQL 里，比如：

- 产品表
- FAQ 表
- 帮助中心表
- 接口文档表

你可以这样做：

### 17.1 先挑文本字段

例如：

- 标题
- 内容
- 摘要
- 备注

### 17.2 组装成可检索文本

例如：

```text
标题：如何创建 API Key
分类：用户管理
正文：进入控制台后，点击 API Keys 管理...
```

### 17.3 对文本切片

如果正文很长，就拆段。

### 17.4 调 embedding 接口

把每段生成向量。

### 17.5 写入向量库

把向量、文本、来源、业务 ID 一起保存。

这样以后用户提问：

```text
怎么生成密钥？
```

系统就能通过语义相似度找到：

```text
如何创建 API Key
```

---

## 18. 一个很实用的表设计思路

如果你做的是“业务数据库 + 向量库分离”模式，可以这样设计：

### 18.1 业务表

保存原始业务数据，例如：

- `faq`
- `documents`
- `articles`

### 18.2 向量表

保存检索用数据，例如：

```text
id
biz_type
biz_id
chunk_text
embedding
source_title
status
created_at
```

这样做的好处是：

- 业务数据和检索数据分开
- 后续重新切片、重新 embedding 更方便
- 不影响原始业务表结构

---

## 19. 一个最小可用示例思路

例如你有一张 FAQ 表：

```text
id | question | answer
```

你可以把它转换成向量库数据：

### 19.1 先拼文本

```text
问题：如何重置密码？
答案：管理员进入后台安全设置后可以重置密码。
```

### 19.2 生成向量

把上面的整段文本转成 embedding。

### 19.3 存入向量库

保存：

- FAQ 的 `id`
- 上面的文本
- 向量

### 19.4 用户提问时检索

如果用户问：

```text
密码忘了怎么办？
```

系统就能召回这条 FAQ。

---

## 20. 什么时候需要重建向量

下面这些情况通常需要重新向量化：

- 原始文档内容改了
- 切片规则改了
- embedding 模型改了
- 元数据策略改了

所以一个成熟系统通常会有：

- 全量重建
- 增量更新
- 删除失效向量

---

## 21. 做向量库最常见的坑

### 21.1 不切片

整篇文档直接向量化，检索效果通常不好。

### 21.2 切片太碎

切得太短，信息上下文不完整，模型读不懂。

### 21.3 没有保存原文

只存向量，不存原文，最后查出来也没法回答。

### 21.4 不做阈值判断

检索到不等于检索对了。

一定要看相似度分数。

### 21.5 把结构化字段也强行向量化

像金额、状态码、时间这些，更适合做过滤条件，不适合主要靠向量检索。

---

## 22. MCP、Tool、向量数据库怎么连起来

把这三者连起来看，其实非常清楚：

### 22.1 向量数据库

负责存储向量和做相似度检索。

### 22.2 Tool

负责把“搜索向量库”这件事暴露成模型可调用的功能。

例如：

```text
searchKnowledge(query, topK)
```

### 22.3 MCP

负责把这个 Tool 以及其他资源、能力规范化地提供给模型。

最终形成：

```text
用户问题
-> 模型
-> MCP 提供的 Tool
-> 向量数据库检索
-> 返回结果
-> 模型组织答案
```

---

## 23. 你现在应该怎么理解

如果你只记一条主线，就记这个：

```text
MCP 是协议层
Tool 是执行能力
向量数据库是检索存储层
```

它们组合起来，就能做出真正可用的 AI 系统。

---

## 24. 适合你的学习顺序

如果你现在是学习阶段，我建议按下面顺序：

1. 先理解 Tool 是什么，知道模型为什么要调用工具
2. 再理解 MCP 是什么，知道为什么需要标准化接入
3. 再学习 embedding 和向量检索
4. 最后把 Tool + 向量数据库 + 大模型串成一个简单 RAG

这个顺序会比较稳。

## 25. 最后的总结

一句话总结：

```text
Tool 让模型能做事
MCP 让模型能规范地接这些能力
向量数据库让模型能查到语义相关的知识
```

如果你把这三件事搞明白，后面你做：

- 智能问答
- 企业知识库
- RAG
- AI 助手
- Agent

思路都会清楚很多。
