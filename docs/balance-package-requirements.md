# 余额套餐需求说明

## 1. 目标

新增一种“余额套餐”。

这个套餐的核心特点是：

- 购买价格为 `0 美元`
- 购买时不扣钱
- 用户购买后，可以基于这个套餐创建 API Key
- 使用这个 API Key 调用模型时，不扣普通套餐额度
- 而是直接从用户钱包余额按量扣费

---

## 2. 套餐定义

### 2.1 套餐类型

系统中的套餐分为两类：

- 普通套餐
- 余额套餐

### 2.2 余额套餐特征

- 套餐售价：`0 美元`
- 购买时不产生消费流水
- 购买的作用是“开通按余额计费权限”
- 真正收费发生在模型调用时

---

## 3. 购买规则

### 3.1 购买条件

用户购买余额套餐时，必须满足：

- 钱包余额 `>= 1.00 美元`

### 3.2 不满足条件时

如果用户余额 `< 1.00 美元`，则不允许购买余额套餐。

提示文案：

```text
当前余额不足 1 美元，无法购买该套餐，请先充值
```

### 3.3 购买成功后的结果

购买成功后：

- 用户获得一个余额套餐购买记录
- 可以基于该套餐创建 API Key
- 不扣钱包余额
- 不写套餐购买扣费流水

---

## 4. API Key 创建规则

### 4.1 创建时必须绑定套餐

用户创建 API Key 时，必须明确选择一个套餐。

可选绑定：

- 普通套餐
- 余额套餐

### 4.2 绑定结果

- 如果绑定普通套餐，则该 API Key 走普通套餐逻辑
- 如果绑定余额套餐，则该 API Key 走余额扣费逻辑

---

## 5. 调用计费规则

### 5.1 普通套餐 Key

如果 API Key 绑定的是普通套餐：

- 只走普通套餐额度校验
- 扣普通套餐额度
- 不扣钱包余额
- 即使钱包有钱，也不能自动切到余额扣费

### 5.2 余额套餐 Key

如果 API Key 绑定的是余额套餐：

- 不校验普通套餐额度
- 不消耗普通套餐额度
- 直接按本次请求金额从钱包余额扣费
- 即使用户还有普通套餐，也不能自动切换到普通套餐

---

## 6. 自动切换规则

系统禁止自动切换套餐类型。

### 6.1 禁止场景

#### 场景一：余额套餐 Key

如果当前 API Key 绑定的是余额套餐：

- 余额不足时，直接失败
- 不能自动切换到普通套餐

#### 场景二：普通套餐 Key

如果当前 API Key 绑定的是普通套餐：

- 套餐额度不足时，直接失败
- 不能自动切换到余额扣费

### 6.2 核心规则

```text
系统只根据当前 API Key 绑定的套餐类型进行扣费，不允许在普通套餐和余额套餐之间自动切换。
```

---

## 7. 余额套餐调用前校验

余额套餐 API Key 发起请求时，至少需要通过以下校验：

### 7.1 最低余额门槛

当前钱包余额必须：

```text
>= 0.50 美元
```

如果余额 `< 0.50 美元`，则直接拒绝调用。

提示文案：

```text
当前余额不足，请先充值
```

### 7.2 本次请求金额校验

即使余额 `>= 0.50`，也必须满足：

```text
当前余额 >= 本次请求应扣金额
```

如果余额不足以支付本次请求，也必须拒绝调用。

提示文案：

```text
当前余额不足，无法完成本次调用，请先充值
```

---

## 8. 扣费时机

余额套餐的扣费时机为：

- 请求完成后
- 根据实际计算出的 `userAmount` 扣减钱包余额

### 8.1 扣费内容

- 扣减 `wallets.balance`
- 增加 `wallets.total_consume`
- 记录交易流水
- 记录请求日志

### 8.2 扣费流水类型

建议使用：

- `transaction_type = CONSUME`
- `direction = OUT`

---

## 9. 日志与统计

余额套餐请求成功后，应保留现有日志能力：

- 写入 `request_logs`
- 写入钱包流水 `transactions`
- 保留 `user_amount`
- 保留 `cost_amount`

这样后续可以统计：

- 用户用了多少钱
- 哪个 API Key 扣的钱
- 哪个套餐类型触发了扣费

---

## 10. 业务示例

### 示例 1：购买余额套餐

用户钱包余额：`0.80`

操作：购买余额套餐

结果：

- 购买失败

提示：

```text
当前余额不足 1 美元，无法购买该套餐，请先充值
```

### 示例 2：余额套餐调用成功

用户钱包余额：`5.20`

本次请求应扣金额：`0.18`

结果：

- 调用成功
- 钱包余额变成 `5.02`

### 示例 3：余额套餐调用失败（低于最低门槛）

用户钱包余额：`0.45`

结果：

- 禁止调用

提示：

```text
当前余额不足，请先充值
```

### 示例 4：余额套餐调用失败（不够支付本次请求）

用户钱包余额：`0.60`

本次请求应扣金额：`0.80`

结果：

- 禁止调用

提示：

```text
当前余额不足，无法完成本次调用，请先充值
```

---

## 11. 实现原则

- 用户可以同时拥有普通套餐和余额套餐
- 每个 API Key 只能绑定一个套餐
- 请求时只根据当前 API Key 绑定的套餐类型进行扣费
- 余额套餐只扣余额，不扣普通套餐额度
- 普通套餐只扣套餐额度，不扣余额
- 两种套餐之间不允许自动切换

---

## 12. 一句话结论

余额套餐是一种“0 美元购买、按余额实时扣费”的套餐类型：

- 购买时不扣钱
- 但余额必须 `>= 1.00`
- 创建出的 API Key 只按余额扣费
- 不消耗普通套餐额度
- 不允许自动切换到普通套餐
- 使用时余额必须 `>= 0.50`
- 且余额必须足够支付本次请求金额
