# AI 多对话并发说明

## 背景

当前项目对外提供 OpenAI 兼容接口：

- `POST /v1/chat/completions`
- `POST /chat/completions`
- `POST /v1/responses`
- `POST /responses`
- `POST /v1/messages`
- `POST /messages`
- `POST /v1/v1/messages`

这些接口主要由 `GatewayChatController` 接收请求，再交给 `GatewayChatService` 完成鉴权、路由、上游转发、日志记录和扣费。

用户所说的“多个 AI 对话同时进行”，在后端表现为：同一个用户、同一个 API Key、不同用户，或者不同浏览器窗口，同时发起多个聊天请求。

## 当前结论

当前代码没有显式写业务层并发控制，但普通 AI 对话请求可以并发执行。

原因是项目运行在 Spring Boot Web 服务上，HTTP 请求会由 Web 容器的请求线程池处理。只要没有在业务代码中加全局锁、单线程队列或共享阻塞状态，多个请求就不会天然排队成单线程。

也就是说，用户可以同时打开多个 AI 对话窗口，每个窗口发送自己的请求，后端会把它们当成多个独立 HTTP 请求处理。

## 当前并发处理方式

### 1. 普通非流式请求

非流式请求会在当前请求线程中完成：

1. 解析 Authorization。
2. 校验 API Key。
3. 根据 model 解析模型路由。
4. 校验用户套餐或余额权限。
5. 请求上游模型接口。
6. 解析 usage。
7. 写入请求日志、扣费流水和日统计。
8. 返回上游响应。

这类请求本身可以并发。并发能力主要受以下因素影响：

- Tomcat 请求线程池大小。
- 数据库连接池大小。
- 上游模型接口的响应速度和限流。
- 当前服务器 CPU、内存、网络能力。

### 2. 流式请求

流式请求会通过 `ResponseBodyEmitter` 返回 SSE 数据。

当前实现中，每个流式请求会创建一个新的后台线程读取上游流，并持续发送给客户端。

这种方式可以支持多个流式对话同时进行，但它的扩展性有限。并发量较小时没有明显问题；并发量升高后，线程数量会跟着请求数增长，可能带来以下风险：

- 线程数过多导致内存占用升高。
- 上游流长时间不结束，占用线程和连接。
- 客户端断开后，后台线程需要及时释放资源。
- 大量 SSE 请求同时存在时，Tomcat、OkHttp、数据库连接都可能成为瓶颈。

后续建议把“每个流式请求新建线程”改成受控线程池。

### 3. 余额扣费

当前余额扣减使用数据库 SQL：

```sql
update wallets
set balance = balance - #{amount},
    total_consume = total_consume + #{amount},
    updated_at = now()
where user_id = #{userId}
  and balance >= #{amount}
```

这个扣减是数据库层面的原子更新。多个请求同时扣费时，不会简单地把余额扣成负数。

但是当前代码在扣费前会先查询钱包余额，再执行扣减。因此在极端并发下，交易流水里的 `balanceBefore`、`balanceAfter` 可能不是最准确的真实前后余额。

实际余额安全性基本可控，但流水展示仍建议后续优化。

### 4. 用量统计

每次请求结束后会写入：

- `request_logs`
- `transactions`
- `usage_daily`
- API Key 已用额度

这些操作支持并发写入。需要关注的是数据库唯一索引、聚合更新 SQL 和事务边界是否能承受高并发写入。

如果后续请求量变大，可以把日志和日统计改为异步队列处理。

## 会话隔离说明

### 普通 OpenAI 兼容聊天

如果客户端每次请求都传完整 `messages`，后端不保存聊天上下文，那么每个对话窗口天然隔离。

这种模式下，后端不需要知道“这是第几个对话窗口”。客户端自己维护上下文即可。

示例：

```json
{
  "model": "gpt-xxx",
  "messages": [
    { "role": "user", "content": "你好" }
  ],
  "stream": true
}
```

多个窗口只要各自传自己的 `messages`，就可以同时请求。

### 服务端 Agent 会话

如果使用本地 agent/session 功能，后端会保存会话、消息和工具调用记录。

这种模式下需要注意：同一个 session 如果同时发起多条消息，可能出现上下文顺序混乱。例如：

1. 用户在同一会话里连续发送 A 和 B。
2. A 还没完成，B 已经开始执行。
3. 两个请求同时读写同一份 session 消息。
4. 最终历史记录顺序可能和用户预期不一致。

因此服务端保存上下文的会话模式，建议后续增加“同一 session 串行执行”或“请求队列”。

注意：这是针对同一个 session 的保护，不是限制所有用户只能单线程。

## 当前风险点

### 风险 1：流式请求线程不受控

当前每个流式请求都会创建一个线程。

建议改造为：

- 配置专用 `Executor`。
- 设置核心线程数、最大线程数和队列长度。
- 超出容量时返回明确错误，例如 `429` 或 `503`。
- 增加流式请求超时和客户端断开清理。

### 风险 2：缺少用户级并发限制

当前用户可以同时发起很多请求。短期可用，长期可能被单个用户占满资源。

建议增加限制：

- 单个 API Key 最大并发数。
- 单个用户最大并发数。
- 单个 IP 最大并发数。
- 全局最大流式请求数。

超限时返回：

```json
{
  "error": {
    "message": "Too many concurrent requests",
    "type": "rate_limit_error"
  }
}
```

### 风险 3：同一服务端会话缺少互斥

如果 agent/session 是服务端状态，就需要防止同一 session 并发写入。

建议策略：

- 不同 session 可以并发。
- 同一 session 内请求串行。
- 如果同一 session 已有任务在跑，新请求可以返回 `409`，或进入会话队列。

### 风险 4：扣费流水前后余额可能不准确

实际扣费 SQL 是安全的，但交易流水里的前后余额来自扣费前查询。

建议后续改为：

- 扣费时使用数据库事务锁定钱包行。
- 或扣费 SQL 返回扣费后的余额。
- 或扣费后重新查询真实余额，再写交易流水。

### 风险 5：上游限流会影响本地并发体验

本地支持并发，不代表上游模型也允许无限并发。

需要根据不同 provider/token 增加：

- 上游 key 并发限制。
- 上游 key QPS 限制。
- 429 自动重试策略。
- 多 key 轮询或熔断。

## 推荐改造顺序

### 第一阶段：文档和确认

目标是明确系统当前并发行为，不改业务逻辑。

需要确认：

- 普通聊天是否允许同一用户多窗口并发。
- 流式聊天是否允许多窗口并发。
- agent/session 是否需要同一会话串行。
- 是否要限制单用户或单 API Key 最大并发数。

### 第二阶段：基础并发保护

建议先做最小改造：

1. 增加流式请求专用线程池。
2. 增加全局流式并发上限。
3. 增加单 API Key 并发上限。
4. 并发超限时返回清晰错误。

### 第三阶段：会话级保护

如果继续使用本地 agent/session：

1. 为同一 session 增加运行中状态。
2. 同一 session 同时请求时返回 `409 Conflict`。
3. 或增加 session 请求队列。
4. 任务结束后释放 session 锁。

### 第四阶段：扣费和统计优化

请求量变大后建议优化：

1. 钱包扣费流水改为更严格的事务模型。
2. 请求日志异步写入。
3. `usage_daily` 异步聚合。
4. API Key 使用额度增加原子更新和并发测试。

## 建议配置项

后续可以在 `application.yml` 增加：

```yaml
gateway:
  concurrency:
    max-global-requests: 200
    max-global-streams: 50
    max-user-requests: 20
    max-api-key-requests: 10
    max-session-requests: 1
  stream:
    core-threads: 16
    max-threads: 64
    queue-capacity: 200
    timeout-ms: 300000
```

建议含义：

- `max-global-requests`：全站最大同时请求数。
- `max-global-streams`：全站最大同时流式请求数。
- `max-user-requests`：单个用户最大同时请求数。
- `max-api-key-requests`：单个 API Key 最大同时请求数。
- `max-session-requests`：单个服务端会话最大同时请求数，默认应为 1。
- `stream.core-threads`：流式线程池核心线程数。
- `stream.max-threads`：流式线程池最大线程数。
- `stream.queue-capacity`：流式任务排队容量。
- `stream.timeout-ms`：流式响应最长持续时间。

## 验证用例

### 用例 1：同一用户多窗口普通对话

步骤：

1. 使用同一个 API Key。
2. 同时发送 5 个非流式 `/v1/chat/completions` 请求。
3. 每个请求使用不同 `messages`。

预期：

- 5 个请求都能独立返回。
- 请求日志生成 5 条。
- 余额扣费 5 次。
- 不出现上下文串话。

### 用例 2：同一用户多窗口流式对话

步骤：

1. 使用同一个 API Key。
2. 同时发送 5 个 `stream=true` 请求。
3. 客户端分别读取 SSE。

预期：

- 每个窗口都能持续收到自己的 SSE。
- 不同窗口内容不混合。
- 请求结束后均写入日志和扣费。

### 用例 3：余额不足并发请求

步骤：

1. 准备一个余额只够少量调用的用户。
2. 同时发送多个会产生扣费的请求。

预期：

- 成功请求会正常扣费。
- 余额不足的请求失败。
- 钱包余额不会变成负数。

### 用例 4：同一 agent session 并发请求

步骤：

1. 使用同一个服务端 session。
2. 在第一个请求未完成时，立刻发送第二个请求。

预期：

- 当前版本需要重点观察消息顺序和上下文是否混乱。
- 后续改造后，同一 session 应返回 `409` 或排队执行。

## 最终建议

当前版本可以支持用户打开多个 AI 对话同时使用。

短期重点不是“让它能并发”，而是“让并发可控”。最优先应处理流式线程池和单用户/API Key 并发上限，其次再处理同一 agent session 的串行保护和扣费流水精度。

## 当前实现状态

已完成基础并发保护：

1. 增加 `gateway.concurrency` 配置项。
2. 增加 `GatewayConcurrencyProperties`，用于绑定并发和流式线程池配置。
3. 增加 `GatewayConcurrencyConfig`，提供 `gatewayStreamTaskExecutor` 专用流式线程池。
4. 增加 `GatewayConcurrencyLimiter`，控制全局请求数、全局流式请求数、单用户请求数、单 API Key 请求数。
5. `GatewayChatService` 已接入并发许可。
6. 上游 SSE 流式转发已从每次 `new Thread` 改为使用受控线程池。
7. 流式请求会一直持有并发许可，直到上游流结束或异常结束后释放。
8. 支持在用户维度单独设置并发额度。

尚未完成：

1. `max-session-requests` 配置已预留，但同一 agent session 串行保护尚未接入。
2. 钱包扣费流水的 `balanceBefore`、`balanceAfter` 并发精度仍建议后续继续优化。
3. 请求日志和日统计目前仍是同步写入，高并发场景可继续改为异步队列。

## 单用户并发设置

用户表新增字段：

- `max_concurrent_requests`：该用户最大同时请求数。
- `max_concurrent_streams`：该用户最大同时流式请求数。

含义：

- 值为 `null` 或 `0` 时，使用全局默认配置。
- `max_concurrent_requests` 会覆盖该用户的请求并发上限。
- 用户设置了 `max_concurrent_requests` 后，该用户的单 API Key 默认并发限制也会同步放宽到同一数值，但用户总并发仍然只按该用户上限计算。
- `max_concurrent_streams` 只限制该用户同时存在的真实上游 SSE 流式请求。
- 全局上限始终优先生效。例如全局 `max-global-streams` 是 50，即使某个用户设置为 100，也最多只能在全站 50 的总池子里竞争。

后台控制台已支持：

- 创建用户时设置“请求并发”和“流式并发”。
- 编辑用户详情时修改“请求并发”和“流式并发”。
- 用户列表展示当前并发配置。

推荐配置方式：

- 普通用户：请求并发 `5`，流式并发 `2`。
- 高级用户：请求并发 `20`，流式并发 `10`。
- VIP 用户：请求并发 `50`，流式并发 `20`。
- 不想单独限制时填 `0`，走全局默认。
